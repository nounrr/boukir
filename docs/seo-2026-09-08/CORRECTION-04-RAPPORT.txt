URL STABLES
Les mêmes slugs sont utilisés sous /fr et /ar, avec canonical et alternates FR/AR.
Les ID ancrent chaque page dans le catalogue. Les slugs sont enregistrés dans
src/lib/catalog/registry.ts et brands.json : ils ne sont pas recalculés à chaque
lecture du nom de la catégorie ou de la marque. Ne pas les renommer sans 308.
Exemples :
https://boukirdiamond.com/fr/categories/73-ciment
https://boukirdiamond.com/ar/categories/73-ciment
https://boukirdiamond.com/fr/categories/73-sable
https://boukirdiamond.com/fr/categories/73-gravette
https://boukirdiamond.com/fr/categories/75-etancheite-bitume

https://boukirdiamond.com/fr/categories/53-plomberie
https://boukirdiamond.com/fr/marques/37-danosa

Le périmètre initial comprend aussi les pages générales catégories 73, 36 et 10.
Les autres catégories gardent leurs liens historiques filtrés : elles ne sont
pas transformées automatiquement en pages éditoriales sans contenu préparé.
Les marques nouvelles après ce relevé gardent également leur lien filtré jusqu'à
l'ajout d'un slug durable dans le registre. Une référence supprimée donne 404.

CHOIX DE CONTENU ET PRODUITS
Chaque page possède H1, title, description, conseil d'achat FR/AR, compteur,
produits avec images disponibles et liens directs, navigation et pagination.
Les listes sont chargées côté serveur par ID catégorie ou marque, 24 produits
par page. Aucun tableau de références produits n'est codé en dur.
Les catégories incluent leurs descendants, conformément à l'API existante.
Les pages ciment, sable et gravette combinent la catégorie 73 avec une recherche
éditoriale fixée ; leurs références actuelles ont été vérifiées par désignation.
L'API de recherche existante consulte aussi les descriptions : contrôler la
pertinence lors des évolutions du catalogue et créer des sous-catégories métier
si une classification plus stricte devient nécessaire.
La page 48 décrit l'outillage et les fournitures de pose ; elle ne prétend pas
vendre des carreaux de revêtement. Une telle famille reste à créer si des
références de carreaux sont effectivement ajoutées au catalogue.
Les prix nuls sont affichés « Prix à confirmer », sans inventer de prix.

FILTRES, PAGINATION ET LANGUES
- /shop?category_id=... et /shop?brand_id=... restent disponibles et leur logique
  de filtrage/noindex est conservée.
- « Affiner » ouvre cette boutique filtrée avec l'ID et la recherche de la page.
- Un filtre supplémentaire placé sur une URL éditoriale redirige vers /shop,
  en conservant les filtres et en imposant l'ID de la sélection de départ.
- La pagination éditoriale est rendue côté serveur. Page 2 a un canonical propre
  avec ?page=2 et des liens précédent/suivant ; elle n'est pas ramenée à page 1.
  Seules les premières pages entrent dans le sitemap. Les numéros invalides ou
  hors catalogue donnent 404 ; ?page=1 a le canonical sans paramètre.
- Les slugs inconnus sont rejetés avant tout appel produits.
- FR/AR sont les versions éditoriales. EN/ZH conservent la boutique filtrée ;
  une visite d'un slug connu dans ces langues y est redirigée.
- Les Link hreflang automatiques de next-intl sont désactivés pour éviter
  d'annoncer quatre versions quand seules FR/AR sont éditoriales. Les alternates
  HTML des autres pages, définis par leurs métadonnées, restent conservés.

SITEMAP
backend/routes/ecommerce/catalogPages.js expose /api/ecommerce/products/catalog-pages.
Il compte les produits publiés non supprimés par catégorie, descendants compris,
et par marque, sans descriptions ni variantes. L'export alimente la sélection
des pages non vides dans le sitemap du lot 03. Trois contrôles légers per_page=1
vérifient les sélections ciblées ciment/sable/gravette.
Une erreur API interrompt la génération, sans retirer silencieusement les pages.
Aucune date lastModified artificielle n'est ajoutée aux textes éditoriaux.
Le contrôle global de nombre/taille est conservé après ajout des nouvelles URL.
scripts/check-sitemap.mjs inclut maintenant ces pages hors mode --fixture.

LIMITES DE LA VÉRIFICATION
Le rendu serveur a été exécuté localement sans lancer un serveur HTTP. Le contrôle
automatique avait refusé ce lancement (« blocked by policy ») au lot 01.
Les déclenchements 404/noindex et la pagination sont testés dans le code réel ;
les statuts HTTP et les interactions sur la nouvelle version doivent être
recontrôlés après publication. Aucune publication n'a été effectuée par l'agent.
Dernier relevé public : HTTP 502 sur les nouvelles pages ET sur l'ancienne boutique.
Ce relevé ne permet donc pas de valider les routes déployées. Voir correction-04-http-actuel.json.

ERREUR DE BUILD SIGNALÉE SUR LE SERVEUR
Dans /var/www/boukirEcom, utiliser :
NEXT_PUBLIC_SITE_URL=https://boukirdiamond.com NEXT_PUBLIC_API_URL=https://boukirdiamond.com npm run build

Enregistrer aussi ces deux valeurs dans .env.production et l'environnement du
service e-commerce. Une valeur déjà exportée prime sur le fichier dotenv.
NEXT_PUBLIC_SITE_URL est une origine : ni /fr ni /api, ni localhost en production.
Après réussite, redémarrer le service e-commerce via son gestionnaire habituel
avec ces mêmes valeurs. Ne pas lancer deux processus sur son port.
L'avertissement baseline-browser-mapping n'est pas la cause de cette erreur.
Guide détaillé : ecom/docs/deploiement-seo.md.
Le build local final a réussi avec les variables explicites ci-dessus.
